# Candidate harness survey

Researched 2026-09-22. This note widens the field beyond the four harnesses already examined in [`execution-paths.md`](./execution-paths.md) (Codex SDK/CLI, Claude Code CLI, OpenCode SDK/server, Pi). It surveys eleven further candidates — Aider, Cline, Continue, OpenHands, Goose, Gemini CLI, Qwen Code, GitHub Copilot CLI, Sourcegraph Amp, Cursor CLI, Charm Crush, and Factory Droid — against the same decisive question and the same execution-control columns, so the two notes compose into one adapter-selection picture.

Labels used below, matching `execution-paths.md`:

- **Documented**: stated by the product's current primary documentation, official repo, or public source.
- **Inference**: an architectural conclusion drawn from documented behavior.
- **Prototype**: behavior the documentation does not settle and must be tested with the intended account and CLI version.

## Research conclusion

None of the eleven candidates beats the three adapters `execution-paths.md` already recommends (Codex SDK, Claude Code CLI, OpenCode/Pi RPC) on the decisive question plus execution-control maturity. Three are worth carrying into a future adapter-selection ticket as real candidates, in descending order of documented strength:

- **Factory Droid** (`droid exec`) is the strongest new candidate. Its plan allowance is consumed first across rolling 5-hour/7-day/30-day windows before falling back to metered "Extra Usage," it has the most granular documented permission tiers (`--auto low|medium|high`, `--skip-permissions-unsafe`) and the richest structured-output surface (JSON-RPC with live `droid.request_permission` events) of any harness surveyed, including the original four. ([Factory pricing](https://docs.factory.ai/pricing/individuals), [droid exec overview](https://docs.factory.ai/droid-exec/overview))
- **Google Gemini CLI** has the best-documented genuine subscription-*request*-allowance shape (Google AI Pro/Ultra OAuth, 1,500–2,000 requests/day, explicitly distinguished from the separately-billed API-key path in the same doc), and that cached OAuth credential is confirmed to carry into headless/`-p` mode. ([Gemini CLI quota and pricing](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md), [Gemini CLI authentication](https://geminicli.com/docs/get-started/authentication/))
- **GitHub Copilot CLI** has the most unambiguous documentation that CLI usage draws the *same* plan-based premium-request allowance as interactive Copilot Chat, with no per-token trapdoor for standard use. ([Copilot billing: requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests))

**Cline** is the one candidate that reproduces the *positive* mirror image of Pi's Claude problem: its Claude Code provider mode is documented to use "your Claude subscription limits instead of API token billing," i.e. it is a real subscription-allowance path for Claude specifically, at the cost of degraded streaming and caching. ([Cline: Claude Code provider](https://docs.cline.bot/provider-config/claude-code))

Everything else surveyed is disqualified or not applicable: Aider and Continue have no first-party subscription-login concept (API-key/own-platform-account only); OpenHands has a real subscription path but only for ChatGPT, not Claude; Goose, Amp, Crush, and Qwen Code's now-dead free OAuth tier all turn out to be credit-metered or per-token-billed under a "subscription" label, the same disqualifying shape as Pi→Claude; Cursor CLI's subscription path evaporates the moment BYOK is introduced, which is exactly the scenario an orchestrator wanting model choice would hit.

**Pre-dispatch quota signal — this is the scarcest finding across all fifteen harnesses now surveyed (the original four plus these eleven).** Nothing in this batch documents a clean, scriptable, remaining-plan-allowance check that can run *before* a job is dispatched:

- **Amp's `amp usage` command** is the closest real thing found: a documented, non-interactively runnable CLI command that reports the current remaining Amp credit balance before you spend it. ([Amp pricing](https://ampcode.com/docs/pricing)) But it reports a dollar *credit* balance under pass-through provider pricing, not a flat plan-allowance percentage, and whether it emits machine-parseable (JSON) output is unconfirmed — **Documented** that the command exists, **Prototype** whether it is orchestrator-usable.
- **Gemini CLI's absence of a pre-dispatch check is itself confirmed by the maintainers' own issue tracker**, not just an unchecked gap: open issues explicitly ask for "remaining quota" visibility and confirm only post-hoc, session-scoped `/stats` exists. ([gemini-cli #24094](https://github.com/google-gemini/gemini-cli/issues/24094), [gemini-cli #13842](https://github.com/google-gemini/gemini-cli/issues/13842))
- **GitHub Copilot's `/usage`** and **Factory's `/limits`** both exist but are documented as interactive, session-bound commands, not standalone pre-flight checks a router could shell out to cheaply.
- No candidate exposes anything resembling Anthropic's own rate-limit headers/API (`anthropic-ratelimit-*-remaining`, `GET /v1/organizations/rate_limits`) mapped to a *plan* allowance rather than an API tier. ([Anthropic rate limits](https://docs.anthropic.com/en/api/rate-limits))

Conclusion for Fleet: the local allowance state machine `execution-paths.md` already calls for (fed by successful runs and positively identified exhaustion/rate-limit errors, not token accounting) remains necessary. No harness surveyed — old four or new eleven — removes that requirement. If Fleet wants the closest thing to a real pre-dispatch signal it currently has evidence for, `amp usage` deserves a live prototype; everything else is post-hoc-only.

## Adapter notes

### Factory Droid

**Documented.** `droid exec` is the noninteractive one-shot runner (`droid exec "<prompt>"`), authenticated with `FACTORY_API_KEY`. Model via `-m/--model` or `custom:`-prefixed entries in `~/.factory/settings.json`, plus `--reasoning-effort`. Permission policy is the most granular surveyed: `--auto low|medium|high` tiers (file edits → builds/tests/commits → remote writes/deployments/migrations), `--restrict-tools`/`--additional-tools`/`--disabled-tools`, and an explicit unsafe bypass `--skip-permissions-unsafe` that Factory's own docs say to use "only in completely isolated environments such as Docker containers, throwaway VMs, or ephemeral CI runners." Session continuation via `--session-id`/`--fork`; `-w/--worktree` isolates the working tree (not a full sandbox) for parallel fan-out. Structured output spans `text|json|stream-jsonrpc`, and the JSON-RPC stream exposes live `droid.request_permission` notification events — the richest programmatic mid-run control surface found in this survey. On an autonomy-boundary violation, Droid "stops immediately ... performs no partial changes," with documented exit codes `0`/`1`/`2`. ([droid exec overview](https://docs.factory.ai/droid-exec/overview), [CLI reference](https://docs.factory.ai/reference/cli-reference), [pricing](https://docs.factory.ai/pricing/individuals))

**Limit.** No built-in sandbox — isolation is explicitly the operator's job. `/limits` (usage/allowance visibility) is documented only as an interactive TUI command; whether it is scriptable via `droid exec --output-format json` is unconfirmed. **Prototype** before treating any Droid usage signal as pre-dispatch-checkable.

### Gemini CLI

**Documented.** Headless mode triggers automatically in non-TTY contexts or via `-p`/`--prompt`, with `--output-format json|stream-json`; `stream-json` emits `init`/`message`/`tool_use`/`tool_result`/`error`/`result` events including per-model token breakdowns. `--approval-mode default|auto_edit|yolo|plan` controls tool auto-approval, and the built-in sandbox (`--sandbox`/`-s`, `GEMINI_SANDBOX`) auto-enables under `yolo` as a safety compensation. Session resume via `--resume`/`-r`, plus separate git-state checkpointing restorable via `/restore`. Documented exit codes distinguish general/API error (`1`), input error (`42`), and turn-limit exceeded (`53`). Critically: "Headless mode will use your existing authentication method, if an existing authentication credential is cached" — the Google-account plan-quota OAuth is not forced over to API-key billing just because a job runs headless. ([headless docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/headless.md), [authentication](https://geminicli.com/docs/get-started/authentication/), [configuration](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md), [session management](https://geminicli.com/docs/cli/session-management/))

**Limit.** `/stats model` is explicitly session-scoped, not account/day-cumulative, and two open maintainer-tracked issues confirm there is no built-in way to see daily-quota-remaining. ([gemini-cli #13842](https://github.com/google-gemini/gemini-cli/issues/13842), [gemini-cli #24094](https://github.com/google-gemini/gemini-cli/issues/24094)) A quota-exhaustion failure is only visible after the fact, via exit code `1`/`53` or a JSON `error` field.

### GitHub Copilot CLI

**Documented.** `copilot -p "<prompt>"` (or piped stdin) is the noninteractive surface; default model is Claude Sonnet 4.5, switchable via `/model`. Tool policy is explicit and CLI-native: `--allow-all-tools`, `--allow-tool='shell(COMMAND)'`, `--deny-tool='shell(COMMAND)'`, per-MCP-server allow rules. Two sandbox layers exist: a local `/sandbox enable` mode restricting filesystem/network/capability access, and a cloud sandbox via `copilot --cloud` inheriting Copilot cloud-agent policies. Headless/CI auth is via `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN` env vars, and the billing doc's "regardless of the underlying AI model used" wording applies to the CLI interaction itself, not the credential type — so token-based headless auth still draws the plan's premium-request allowance. Usage is checkable via `/usage` in-session or the `github.com/settings/copilot` "Usage this month" page; `/context` and `/compact` (95% auto-compaction) manage context-window usage. ([Copilot CLI concepts](https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli), [billing: requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests), [authenticate Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli))

**Limit.** Session resume, structured (JSON) output, and a formal failure taxonomy were not found in the pages reviewed — flagged as open gaps, not confirmed absent. `/usage` requires an already-running session; no standalone pre-dispatch quota check or documented REST/GraphQL usage endpoint was found for individual accounts (GitHub does document org-level Copilot usage metrics APIs for admins, which were not checked in this pass). **Prototype/needs follow-up**, not confirmed either way.

### Cline (Claude Code provider mode)

**Documented.** Cline's own docs state its Claude Code provider "Uses your Claude subscription limits instead of API token billing," requiring the official `claude` CLI to be installed and authenticated separately, with disclosed trade-offs: responses "may not stream token-by-token," and image uploads/prompt caching are limited. This applies only when Cline is configured to shell out to Claude Code — Cline's native Anthropic/OpenAI/OpenRouter/Bedrock/Vertex providers are plain API-key billing. The CLI itself supports `cline "prompt"` one-shot, `--json` for NDJSON streaming, `--yolo` for full auto-approve, and `--zen` to dispatch to a background daemon; `--data-dir`/`CLINE_SANDBOX=1` enables an isolated local-state sandbox mode (not confirmed to be container-based). Failure taxonomy is HTTP-status-shaped (400/401/402/403/429/500/502/503 plus `content_filter`/`context_length_exceeded`). ([Claude Code provider](https://docs.cline.bot/provider-config/claude-code), [CLI README](https://github.com/cline/cline/blob/main/apps/cli/README.md), [API errors](https://docs.cline.bot/api/errors))

**Limit.** No pre-dispatch quota check: Cline's own error docs state remaining-usage visibility is not addressed, only a post-hoc 402 once credits/allowance are exhausted. **Prototype** the streaming/caching degradation before treating this as a full-fidelity Claude adapter.

### OpenHands

**Documented.** `LLM.subscription_login()` opens a browser OAuth flow for OpenAI (ChatGPT Plus/Pro) specifically — "OpenAI subscription is the first provider we support. More subscription providers will be added in future releases" — caching credentials under `~/.openhands/auth/` with auto-refresh, and stating this lets you "access OpenAI's Codex models without consuming API credits." Headless mode (`openhands --headless -t "..."`, `--json`) always runs in always-approve mode; the Docker Runtime is a genuine sandbox ("arbitrary code can be run safely without risking the host system"), the strongest built-in isolation found among the eleven new candidates. Usage metrics are SDK-native and detailed (`llm.metrics`, `conversation.conversation_stats`, per-call token/cost/latency). ([LLM subscriptions](https://docs.openhands.dev/sdk/guides/llm-subscriptions), [headless CLI](https://docs.openhands.dev/openhands/usage/cli/headless), [Docker runtime](https://docs.openhands.dev/openhands/usage/architecture/runtime), [metrics](https://docs.openhands.dev/sdk/guides/metrics))

**Limit.** No Claude Pro/Max or Copilot subscription login exists; OpenHands Cloud's own path to Claude models is a pay-as-you-go dollar-credit balance, explicitly not a plan allowance. No pre-dispatch quota check is documented for either the ChatGPT OAuth path or the Cloud credit path.

### Google account vs. paid-plan pattern (Qwen Code, Goose)

**Documented.** Qwen Code's free `qwen.ai` OAuth tier — architecturally the closest analog to Gemini CLI's free tier — was discontinued 2026-04-15 after its daily quota was cut from 1,000 to 100 two days prior. ([auth docs](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/)) The only currently-live subscription-shaped path is Alibaba Cloud's paid Coding Plan, metered by request count rather than tokens but authenticated via a plan-specific API key rather than OAuth login — a hybrid worth noting since it inverts Pi's problem (key-based auth, but genuinely plan-metered billing). ([Coding Plan](https://www.alibabacloud.com/help/en/model-studio/coding-plan)) Goose has no Claude Pro/Max OAuth at all (open feature request, [issue #3647](https://github.com/block/goose/issues/3647)) and its one real subscription-OAuth path is ChatGPT Plus/Pro via Codex OAuth, with the usage-vs-allowance accounting not independently confirmed. Goose does have a genuine Docker sandbox (non-root, dropped capabilities, resource limits) and `--output-format json|stream-json`. ([Goose providers](https://github.com/block/goose/blob/main/documentation/docs/getting-started/providers.md), [Goose in Docker](https://block.github.io/goose/docs/guides/goose-in-docker/))

**Limit.** Neither harness documents a pre-dispatch quota signal. Qwen Code's own headless/permission/sandbox/resume behavior beyond its Gemini CLI fork lineage was not independently confirmed against Qwen's own docs in this pass — **Inference** only, flagged for follow-up.

### Cursor CLI

**Documented.** `agent -p`/`--print` is the headless surface (`--output-format text|json|stream-json`, plus `--stream-partial-output` for token-level deltas); without `--force`/`--yolo` a print-mode run only proposes changes rather than applying them. `--mode plan|ask`, `--approve-mcps`, `--model`/`--list-models`, and `--resume [chatId]`/`--continue` are all documented CLI flags. Cursor CLI has the most complete *built-in* sandbox flag set surveyed: `--sandbox enabled|disabled`, `--allow-paths`, `--readonly-paths`, `--network`. The decisive subscription question is genuinely three-tiered: (1) Cursor-account login with no BYOK key draws the Pro/Business plan's included allowance; (2) Individual-plan BYOK bypasses the plan entirely and is billed per token by the provider directly; (3) Teams/Enterprise BYOK is billed per token by the provider **and** incurs a documented $0.25/million-token Cursor surcharge drawn from the included allowance — billed twice, not exempted once. ([CLI headless](https://cursor.com/docs/cli/headless), [CLI parameters](https://cursor.com/docs/cli/reference/parameters), [API keys](https://cursor.com/help/models-and-usage/api-keys))

**Limit.** No CLI-native pre-dispatch quota command exists; the only documented usage visibility is the web dashboard's "Spending tab." Cancellation semantics and a formal failure taxonomy were not found in the pages reviewed.

### Sourcegraph Amp

**Documented.** `amp -x "prompt"` is Execute Mode (also auto-triggers when stdout is piped); `--executor local|orb|runner:<id>` chooses where the thread runs, including Amp-hosted "Orb" servers. A dedicated streaming-JSON output mode exists. Pricing is explicit and disqualifying for the subscription-allowance question: "Individuals and non-enterprise workspaces pay pass-through provider API costs with zero markup, no subscription, no commitment, and a $5 minimum credit purchase" — even paid tiers are prepaid credit wallets metered at pass-through provider rates, and Enterprise's flat $1,000 purchase "grants ... $1,000 USD of Amp Enterprise usage," still a credit balance rather than a renewing allowance. ([Amp pricing](https://ampcode.com/docs/pricing), [Execute Mode](https://ampcode.com/docs/cli/execute-mode))

**The one genuinely valuable finding in this survey.** `amp usage` is a documented CLI command runnable non-interactively that reports the current remaining Amp credit balance — "You can buy credits and check your balance in user settings, in workspace settings, or by running `amp usage`." ([Amp pricing](https://ampcode.com/docs/pricing)) This is the closest thing found, across all fifteen harnesses now surveyed by these two notes, to a scriptable pre-dispatch allowance check. **Documented** that the command and the balance semantics exist; **Prototype** whether it emits machine-parseable (JSON) output and whether a dollar-credit balance under pass-through pricing is a usable proxy for "can I dispatch this job" in Fleet's router.

### Charm Crush

**Documented.** BYOK-first via environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`) or an interactive model picker; `--yolo` skips permission prompts, with `permissions allow`/`permissions deny` for tool-level allow/deny lists. Charm's own "Hyper" provider (hyper.charm.land) is described as "subscription-based, with a free tier," but "1 Hypercredit is currently 5¢" and "credits map directly to token costs" — a metered-credit wallet under a subscription label, structurally the same disqualifying shape as Pi→Claude. ([Crush README](https://github.com/charmbracelet/crush/blob/main/README.md), [Hyper FAQ](https://hyper.charm.land/faq))

**Limit.** This is the smallest, least formally documented project surveyed. Open GitHub issues (not formal docs) report that `--yolo` was not originally honored in the noninteractive `crush run` subcommand ([issue #2792](https://github.com/charmbracelet/crush/issues/2792)) and that headless `crush run` has silently ignored a configured large model in favor of the first reasoning-capable catalog entry ([issue #3671](https://github.com/charmbracelet/crush/issues/3671)) — real, primary-repo evidence of headless rough edges, but not resolved in formal documentation. No sandboxing, structured output, cancellation, or usage-reporting command was found documented for Crush itself. **Prototype** current status of both issues before relying on headless Crush for anything.

### Aider and Continue (excluded, for completeness)

**Documented.** Aider has no subscription/OAuth concept whatsoever — API keys only, configured via CLI flags/env vars/`.env`/YAML. ([API keys](https://aider.chat/docs/config/api-keys.html)) Its noninteractive surface is `--message`/`--message-file` plus `--yes-always`; an unofficial Python scripting API is explicitly marked unsupported. ([scripting](https://aider.chat/docs/scripting.html)) Continue's `cn` CLI (`cn -p "prompt"`, `--resume`, `--format json`) has the most granular tool-permission model of any harness surveyed — a three-tier `allow`/`ask`/`exclude` system with glob-pattern overrides, where write/terminal tools auto-downgrade from `ask` to `exclude` in headless mode since there is no human to prompt — but its `cn login` authenticates to Continue's own platform account, not a Claude/ChatGPT/Copilot subscription passthrough. ([tool permissions](https://docs.continue.dev/cli/tool-permissions), [quickstart](https://docs.continue.dev/cli/quickstart))

**Limit.** Neither is a subscription-allowance path for the four providers Fleet cares about. Both are included here only to close out the survey field named in the issue, not as candidates.

## Fleet implications

`execution-paths.md`'s runner contract, normalized failure classes, and "local allowance state machine, not token accounting" conclusion all stand unchanged. This survey adds three candidates worth a future adapter-selection ticket evaluating them against the existing Codex/Claude Code/OpenCode-Pi set — Factory Droid, Gemini CLI, and GitHub Copilot CLI — plus one narrow addition to the Claude side specifically: Cline's Claude Code provider mode, as an alternative shape for reaching a Claude subscription allowance if the native Claude Code CLI adapter proves insufficient. Everything else surveyed should stay excluded unless a specific paid plan Fleet already holds (Alibaba Coding Plan, Cursor Pro/Business without BYOK) makes it worth revisiting.

## Required live prototypes

These behaviors are not settled by documentation and should be tested before any of these harnesses is treated as production-ready:

1. **Factory Droid `/limits`:** confirm whether it (or an equivalent) is scriptable via `droid exec --output-format json` as a true pre-dispatch allowance check, and whether Standard-Usage-window exhaustion produces a distinguishable JSON-RPC event from a transient rate limit.
2. **Gemini CLI headless auth persistence:** confirm across a real OAuth-cached environment that `-p`/headless mode never silently falls back to `GEMINI_API_KEY` billing when both a cached OAuth credential and an API key are present.
3. **GitHub Copilot CLI usage visibility:** determine whether any GitHub REST/GraphQL endpoint (individual-account, not just org-level admin metrics) exposes remaining premium-request allowance without an active interactive session.
4. **Cline Claude Code provider fidelity:** verify the exact functional degradation (streaming granularity, prompt caching, image support) against the native Claude Code CLI adapter Fleet already uses, to decide whether this is a genuine second Claude path or redundant with it.
5. **`amp usage` machine-readability:** confirm whether it supports a JSON/structured output flag, and whether a dollar-credit balance under pass-through pricing is a usable proxy for dispatch-worthiness given Fleet's per-provider allowance model.
6. **Qwen Code Coding Plan mechanics:** if Fleet ever holds this paid plan, confirm the plan-specific API key (`sk-sp-...`) genuinely prevents fallback to token-metered DashScope billing under headless/CI env-var auth.

Until these are captured as fixtures, none of the eleven candidates in this note should be promoted past "documented candidate" to "adapter."
